# GitHub 이슈 처리

하나의 GitHub Issue를 프로젝트의 반복 절차에 따라 처음부터 끝까지 처리한다. 작업 범위와 완료 조건은 Issue의 원본을 따르고, 코드를 수정하기 전에 저장소의 라우팅 규칙과 하네스 문서를 확인한다.

## 필수 처리 순서

1. 처리할 Issue를 확인한다.
2. 관련 프로젝트 지침과 라우팅된 원본 문서를 읽는다.
3. 작업 트리를 확인하고, 현재 동기화된 `main`(또는 사용자가 지정한 기준 브랜치)에서 피처 브랜치를 만든다.
4. Issue, 범위, 시도 예산, 기존 작업, 승인 상태를 사전 점검한다.
5. 승인된 범위만 구현한다.
6. Issue별 테스트를 실행하고 모든 Issue 종료 조건을 평가한다.
7. 로컬에서 `npm run verify`를 실행한다.
8. 모든 로컬 검증과 종료 조건이 통과했을 때만 Issue 완료 코멘트를 작성한다.
9. 승인된 변경만 커밋한다.
10. 피처 브랜치를 푸시한다.
11. Issue와 완료 코멘트를 연결한 PR을 `main` 대상으로 만든다.
12. 브랜치, 커밋, PR, 검증 결과, 보존한 무관 변경을 보고한다.

6~8단계를 건너뛰거나 순서를 바꾸지 않는다. Issue 코멘트는 커밋·푸시·PR보다 먼저 작성하며, 실행하지 않았거나 실패한 검증을 근거로 성공을 주장하지 않는다.

## 라우팅과 범위

- 작업 라우팅은 먼저 `AGENTS.md`를 읽어 확인한다.
- 구현 전에 관련 GitHub Issue를 읽는다.
- 업무 규칙은 `docs/01-requirements.md`를 읽는다.
- 아키텍처와 구현 제약은 `docs/06-architecture.md`를 읽는다.
- SSOT 권위, 충돌, 승인, 파괴적 작업, 증거, 비밀 보호는 `docs/harness/01-SSOT.md`를 읽는다.
- 검증 기준과 결과 판정은 `docs/harness/02-verification.md`를 읽는다.
- 판정 이후의 반복, PR·CI 진입, 인계, 사람 승인·반려, 종료는 `docs/harness/03-loop.md`를 읽는다.
- `docs/07-plan.md`와 `docs/HANDOVER.md`는 참고 자료로만 사용한다. 현재 검증 증거로 사용하지 않는다.
- Next.js 코드를 작성하기 전 설치된 버전의 `node_modules/next/dist/docs/` 가이드를 확인한다.

Issue가 없거나, 범위·종료 조건이 모호하거나, 라우팅된 원본이 충돌하거나, 필수 승인이 없거나, 파괴적 대상이 불명확하거나, 명시적인 재개 결정 없이 작업이 이미 완료·폐기된 상태라면 `NEEDS_HUMAN`으로 멈춘다.

## 브랜치와 작업 트리

- 사용자가 다른 기준을 지정하지 않으면 현재 동기화된 `main`에서 시작한다.
- 설명적인 `feature/<짧은-이름>` 브랜치를 사용한다.
- 브랜치를 만들기 전에 `git status`를 확인하고 무관한 변경은 보존한다. 무관한 변경을 조용히 포함·삭제·stash·덮어쓰지 않는다.
- 무관한 미커밋 변경 때문에 기준점이나 범위를 판단할 수 없으면 사용자에게 묻고 멈춘다.
- 사용자가 명시적으로 요청하지 않으면 브랜치 삭제, reset, rebase, merge, 파일 덮어쓰기를 하지 않는다.

## 구현 시도 횟수

`docs/harness/03-loop.md`를 따른다.

- 코드·설정·테스트를 변경하고 검증하면 구현 Attempt 1회다.
- 같은 SHA의 검증 재실행은 Verification Run/Rerun이며 새 Attempt가 아니다.
- 세션·에이전트·worktree가 바뀌어도 횟수를 초기화하지 않는다.
- PR 생성, CI 실행, CI 재실행은 구현 Attempt를 소모하지 않는다.
- 대화 기록만으로 횟수를 추정하지 않는다. 영속적인 Attempt 상태가 없으면 추측하지 말고 `NEEDS_HUMAN`으로 멈춘다.
- Issue의 최대 Attempt 횟수에 도달하면 필요한 증거와 함께 인계한다.

## 로컬 검증 게이트

Issue에 지정된 Issue별 테스트를 먼저 실행한 뒤 다음을 실행한다.

```bash
npm run verify
```

정확한 커밋 SHA, 실행 명령, 환경 요약, 결과를 기록한다. 각 결과의 판정은 `02-verification.md`를 따른다. 성공처럼 보이는 출력만 믿지 말고 명령의 종료와 종료 코드를 확인한다. 후속 재실행이 성공해도 이전 `FAIL` 또는 `BLOCKED` 결과를 보존한다.

PR 진입에 필요한 조건은 모두 다음과 같다.

- Issue별 테스트가 실제로 실행되어 통과했다.
- 모든 Issue 종료 조건을 각각 충족했다.
- 현재 구현 SHA에서 로컬 `npm run verify`가 통과했다.
- 해결되지 않은 `FAIL`, `NOT_RUN`, `BLOCKED`가 없다.
- 필요한 수동 검증 증거가 있다.
- 브랜치·base·head·검증 SHA와 증거가 기록되어 있다.

환경 때문에 검증이 막히면 PASS를 만들려고 코드를 바꾸지 말고 원인을 분류한다. 같은 SHA를 안전하게 다시 실행할 수 있으면 Rerun으로 기록하고, 그렇지 않으면 `NEEDS_HUMAN`으로 인계한다.

## Issue 완료 코멘트

로컬 PR 진입 조건을 통과한 뒤, 커밋 전에 Issue에 간결한 완료 코멘트를 작성한다. 다음 형식을 사용한다.

```text
## 로컬 검증 완료

- Issue: #<번호>
- Attempt: <사용 수> / <최대 수>
- 검증 SHA: <sha>
- Issue별 테스트: PASS (<명령>)
- 종료 조건:
  - <조건>: PASS
- npm run verify: PASS
- 남은 FAIL / NOT_RUN / BLOCKED: 없음
- PR 진입: 가능
```

비밀번호, 토큰, 세션 시크릿, 개인정보, 정제되지 않은 로그를 포함하지 않는다. Issue가 요구하는 증거 형식이 있으면 그 형식을 따른다. 완료 코멘트를 작성할 수 없거나 정식 기록 위치가 불명확하면 커밋·푸시·PR 전에 멈추고 `NEEDS_HUMAN`을 보고한다.

## 커밋·푸시·PR

완료 코멘트 작성이 성공한 뒤 다음을 수행한다.

1. staged diff를 확인하고 무관한 변경이 빠졌는지 확인한다.
2. 저장소가 요구하는 attribution을 포함한 간결한 커밋 메시지로 커밋한다.

```text
[org] Generated with Claude Code - commit message
```

3. 피처 브랜치를 푸시한다.
4. `main` 대상 PR을 만들고 다음을 포함한다.
   - 구현 요약
   - 해당하는 경우 `Closes #<번호>` 형식의 Issue 연결
   - 완료 코멘트 링크
   - 검증한 커밋 SHA
   - Issue별 테스트와 `npm run verify` 결과
   - 보존한 실패·Rerun 기록

PR 생성은 승인이나 머지가 아니다. 사용자가 명시적으로 요청하고 프로젝트 정책이 허용하지 않는 한 PR을 머지하지 않는다.

## PR 이후 CI 실패

CI 실행 자체는 구현 Attempt를 소모하지 않는다.

- CI run, SHA, 첫 실패 게이트, 환경, 정제된 요약을 기록한다.
- 같은 SHA에서 동등한 명령·조건·원인으로 로컬 재현되면 기존 구현·검증 루프로 돌아간다. 코드·설정·테스트 변경은 새 Attempt이고, 환경만 복구하면 Rerun이다.
- 로컬에서 재현되지 않으면 원인을 추측하거나 수정하지 않는다. PR과 증거를 보존하고 Loop State를 `NEEDS_HUMAN`으로 바꾼 뒤 사람의 결정을 기다린다.
- PR head SHA가 검증 SHA와 다르면 기존 PASS를 재사용하지 않는다. 새 head에서 로컬 검증과 Issue 조건을 다시 확인하고 완료 코멘트를 갱신한다.

## 사람 판단과 안전

원본 충돌, 모호한 범위, 불명확한 파괴적 DB 대상, 필수 승인 누락, Attempt 예산 소진, 활성 writer 충돌, 판정할 수 없는 검증 스크립트 오류, 로컬에서 재현되지 않는 CI 실패, 기존 PR 재개와 새 PR 중 선택이 필요한 경우에는 진행하지 말고 사람의 판단을 요청한다.

승인·반려 lifecycle은 다음과 같다.

- 사람의 승인은 PR이 `main`에 머지되어 `MERGED`가 되는 것으로 기록한다.
- 사람의 반려는 PR을 머지하지 않고 닫아 `CLOSED`가 되는 것으로 기록하며, 반려 사유를 남긴다.
- PR을 닫는 것만으로 Issue를 자동 종료하거나 폐기하지 않는다. Issue 종료는 사람의 명시적 결정이 있을 때만 한다.
- CI PASS를 사람의 승인으로 간주하지 않는다.

## 최종 보고

다음 내용을 보고한다.

- Issue 번호와 결과
- 피처 브랜치
- 커밋 SHA와 메시지
- PR URL과 상태
- 로컬 검증 명령과 결과
- Issue 완료 코멘트 결과
- 가능한 경우 CI 상태
- `NEEDS_HUMAN` 결정 또는 보존한 무관 작업 트리 변경

실제로 실행하지 않은 명령, 작성하지 않은 코멘트, 생성하지 않은 커밋·푸시·PR, 수행되지 않은 리뷰·머지·사람의 결정을 완료했다고 주장하지 않는다.
