> 확인해야 하는지와 원본 간의 우선순위를 정한다.

- **상태:** 초안
- **작성일:** 2026-08-26
- **범위:** 재고 도메인, 아키텍처, 개별 작업, 향후 검증 체계의 원본 관계

## 2. 원본 우선순위와 충돌 해결

원본의 우선순위는 전체 문서에 일괄 적용하지 않고 영역별로 적용한다.

1. **재고 도메인 의미와 업무 요구사항**은
   [`docs/01-requirements.md`](../01-requirements.md)를 우선한다.
2. **기술 구현과 시스템 구조**는
   [`docs/06-architecture.md`](../06-architecture.md)를 우선한다.
3. **개별 작업의 범위·상태·완료 증거**는 해당 GitHub Issue를 우선한다.
4. Issue가 도메인 규칙이나 아키텍처 제약을 변경해야 하는 경우, Issue의
   문장만으로 기존 원본을 덮어쓰지 않는다. 먼저 해당 원본을 갱신하고,
   Issue에 변경 이유와 갱신된 원본 링크를 남긴다.
5. 원본 간 충돌이 해소되지 않으면 임의로 구현하지 않고 **미결정**으로
   표시한다. 결정권자, 기한, 관련 Issue가 정해지지 않았다면 각각
   **없음**으로 표시한다.
6. `HANDOVER.md`, `07-plan.md`, README의 요약이나 현재 상태가 원본과 다를
   경우, 해당 문서의 역할 범위 안에서만 참고하고 원본을 조용히 변경하지
   않는다.

### 충돌 처리 정책

1. 참고 문서와 SSOT가 충돌하면 **SSOT를 우선**한다.
2. GitHub Issue와 SSOT가 충돌하면 **`NEEDS_HUMAN`** 상태를 선언하고 사람에게
   판단을 요청한다. 사람의 판단 전에는 구현·문서 갱신·상태 변경을 진행하지
   않는다.
3. SSOT와 SSOT가 충돌해도 **`NEEDS_HUMAN`** 상태를 선언하고 사람에게 판단을
   요청한다. 어느 SSOT를 우선할지 AI가 결정하지 않는다.
4. AI는 충돌이 발생한 경우 자신의 판단대로 행동하지 않는다. 충돌 내용,
   충돌한 원본, 영향 범위와 판단이 필요한 선택지를 명시한다.
5. 사람이 충돌 내용을 확인하고 명시적으로 진행을 지시하면, 그 지시는 해당
   충돌에 대한 보호 정책 우회 승인으로 간주한다. 지시가 없거나 대상·범위가
   불명확하면 계속 진행하지 않는다.
6. 보호 정책 우회는 저장소 작업, 문서, 스크립트, 원격 작업과 CI를 포함한
   모든 적용 지점에서 사용할 수 있다. 단, 사람의 지시가 없었던 사실을
   추정하거나, 비밀·개인정보를 노출하는 행위를 정당화하는 근거로 사용하지
   않는다.

## 3. 보호 정책

### 3.1 변경 승인 보호

- SSOT, 원본 문서, GitHub Issue를 변경하기 전 사람의 명시적 승인을
  확인한다.
- 사람이 SSOT의 수정을 직접 요청한 경우에는 그 요청을 명시적 승인으로
  간주하고, 요청된 범위 안에서 SSOT를 수정한다.
- 사용자가 현재 작업을 직접 요청한 경우에는 그 요청에 포함된 범위 안에서만
  변경한다. 요청에 포함되지 않은 원본·정책·범위는 함께 변경하지 않는다.
- 원본 변경이 필요한 작업은 변경 대상, 이유와 영향 범위를 먼저 밝히고,
  승인 전에는 변경하지 않는다.

### 3.2 파괴적 작업 보호

- 삭제, 초기화, 덮어쓰기, 원격 변경, 커밋, 푸시, 머지처럼 되돌리기
  어렵거나 외부에 영향을 주는 작업은 사람의 명시적 승인 없이 수행하지
  않는다.
- 사용자가 해당 작업을 직접 요청한 경우에도 대상과 범위를 확인하고,
  요청 범위를 벗어난 파괴적 작업은 수행하지 않는다.
- 승인 여부나 대상이 불명확하면 작업을 중단하고 사람에게 확인을 요청한다.

### 3.3 근거·추정 보호

- 원본 문서나 사용자가 제공한 정보로 확인되지 않은 사실·규칙·상태를
  추정해 확정하지 않는다.
- 판단에 사용한 근거와 불확실성을 명시한다.
- 근거가 없거나 원본 간 충돌이 있으면 **미결정** 또는
  **`NEEDS_HUMAN`**으로 표시하고 사람의 판단 전에는 진행하지 않는다.

### 3.4 비밀·개인정보 보호

- 토큰, 비밀번호, API 키, 세션 시크릿, 인증 정보와 개인 식별 정보를
  문서, 로그, 커밋, PR, 외부 메시지에 기록하거나 노출하지 않는다.
- 필요한 경우 값 자체가 아니라 존재 여부, 종류 또는 마스킹된 식별자만
  다룬다.
- 비밀이나 개인정보의 노출 가능성을 발견하면 내용을 복사·전파하지 않고
  즉시 중단한 뒤 사람에게 안전한 처리 방법을 요청한다.

보호 정책 위반 가능성이 있거나 승인·근거가 부족한 경우에는 원칙적으로
작업을 중단한다. 다만 사람이 대상·범위와 영향을 확인한 뒤 명시적으로
진행을 지시한 경우에는 위 충돌 처리 정책의 우회 승인으로 기록하고 진행할
수 있다. 비밀·개인정보의 실제 노출은 사람의 지시만으로 정당화하지 않는다.

## 4. 영역별 기준

### 3.1 재고 도메인

재고 도메인의 원본은 [`docs/01-requirements.md`](../01-requirements.md)이다.
상세 규칙을 이 문서에 다시 쓰지 않고 원본의 해당 절을 따른다. 핵심 범위는
다음과 같다.

- 상품·거점·유통기한으로 구분되는 재고와 로트의 의미
- 입고, 출고, 풀필먼트 이동, 팝업 반출·정산, 조정, 폐기
- FEFO/LEFO 적용 정책과 재고 증감 사유 체계
- 이력·감사 로그, 로그인, 비기능 요구사항
- 범위 제외 및 Definition of Done

도메인 규칙을 해석하거나 변경할 때는 먼저 원본을 확인하고, 변경이 필요하면
해당 원본과 관련 Issue를 함께 갱신한다.

### 3.2 아키텍처

아키텍처의 원본은 [`docs/06-architecture.md`](../06-architecture.md)이다.
상세 설계와 구현 제약은 이 문서를 복제하지 않고 아키텍처 원본을 따른다.
핵심 범위는 다음과 같다.

- 실행 환경, 기술 스택, 계층 및 폴더 책임
- 데이터 흐름과 상태 흐름
- 재고 원장·현재값·트랜잭션 불변식
- FEFO/LEFO, 팝업 정산, 취소·상쇄 기록
- 인증, 시드, 동시성·성능 가정
- 자동화 대상 불변식의 설계

현재 구현에서 후속으로 확정된 사항은 `HANDOVER.md`와 `07-plan.md`에서
확인할 수 있지만, 아키텍처 원본과 충돌하거나 구조적 변경을 포함하면
아키텍처 원본을 먼저 갱신해야 한다.

### 3.3 개별 작업

개별 작업의 원본은 해당 GitHub Issue이다.

현재 Issue 인덱스와 작업 상태는 GitHub에서 확인한다. 이 문서에 현재 Issue 개수를 복제하지 않는다.
Issue가 생성되면 Issue 안에 최소한 다음을 기록한다.

- 작업 목적과 배경
- 관련 요구사항 원본의 경로와 절
- 관련 아키텍처 원본의 경로와 절
- 구현 범위와 비범위
- 완료 조건
- 검증 증거
- 상태, 담당자, 관련 PR
- 원본 문서 변경 필요 여부
- 유지보수 작업이면 [GitHub Issue Form](../../.github/ISSUE_TEMPLATE/maintenance.yml)의
  `종료 조건`, `기계 검증`, `구현 루프 최대 횟수`를 작성한다.
- 구현 루프 최대 횟수의 기본값은 3회이며, 선택한 횟수 안에 검증하지 못하면
  추가 반복 없이 `NEEDS_HUMAN`으로 사람에게 인계한다.
- 각 Issue의 종료 조건 검증 테스트는
  `tests/issues/issue-{Issue 번호}-{기능명}.test.ts` 경로를 사용한다.

이 문서에는 Issue의 전체 내용을 복사하지 않는다. 필요할 때 GitHub Issue를
직접 참조하며, Issue 링크 목록은 Issue가 생성된 뒤 추가한다.

## 4. 변경 관리

| 변경하려는 내용 | 먼저 갱신할 원본 | 작업 기록 |
|---|---|---|
| 재고 업무 규칙·범위·완료 기준 | `docs/01-requirements.md` | 관련 GitHub Issue |
| 기술 구조·불변식·구현 제약 | `docs/06-architecture.md` | 관련 GitHub Issue |
| 특정 기능의 구현 범위·진행 상태 | 해당 GitHub Issue | PR 및 검증 증거 |
| 원본 레지스트리·우선순위·SSOT 규칙 | `docs/harness/01-SSOT.md` | 관련 GitHub Issue |
| 현재 상태·인계 메모 | `docs/HANDOVER.md` | 관련 작업 Issue |

변경 순서는 다음을 따른다.

1. 변경 대상이 도메인인지, 아키텍처인지, 개별 작업인지 분류한다.
2. 해당 원본과 관련 GitHub Issue를 연결한다.
3. 도메인·아키텍처 원본을 바꿔야 하면 원본을 먼저 갱신한다.
4. Issue에 변경 이유, 영향 범위, 완료 조건을 기록한다.
5. 구현과 검증 증거를 Issue 또는 연결된 PR에 남긴다.
6. 원본 우선순위 자체가 바뀐 경우에만 이 SSOT를 갱신한다.

## 6. 구현·검증 반복 절차

- **상태:** 초안 — 사람의 최종 확인 필요
- **원본:** [`docs/harness/03-loop.md`](./03-loop.md)
- **담당:** 미지정
- **기한:** 없음
- **관련 Issue:** 없음

판정 이후의 구현 반복, 동일 SHA 재검증, 세션·에이전트 인계, PR·CI 진입과
복귀, 사람 승인·반려, 종료 절차는 `docs/harness/03-loop.md`를 따른다.
이 문서의 절차와 권장안은 사람의 결정 전까지 강제 규칙으로 사용하지 않는다.

`02-verification.md`의 검증 결과를 이 문서의 Loop State나 Attempt 상태로
덮어쓰지 않는다. 도메인 또는 아키텍처를 변경하는 경우에는 각 원본과
관련 Issue를 별도로 갱신한다.

사람의 승인 결과는 PR의 `MERGED`로, 반려 결과는 머지하지 않은 PR의
`CLOSED`로 기록한다. 반려만으로 작업 전체를 폐기한 것으로 간주하지 않으며,
Issue를 닫을지는 별도 사람의 판단으로 남긴다.

---

## 7. 구현·검증 루프와 원본 관계

`02-verification.md`는 개별 검증 결과를 판정하고, `03-loop.md`는 그 판정
이후의 작업 진행을 결정한다. Issue는 작업별 범위·종료 조건·최대 시도 수를
정한다. PR은 사람이 승인·반려할 변경 단위이며, CI는 PR의 특정 SHA를
검증한다. Issue·원본·검증 결과가 충돌하면 `NEEDS_HUMAN`으로 중단한다.

CI 실행과 CI 재실행은 구현 Attempt에 포함하지 않는다. CI 실패가 로컬에서
동일 SHA·동일 조건으로 재현되면 03-loop의 구현·검증 절차로 복귀하고,
재현되지 않으면 원인 추정 없이 `NEEDS_HUMAN`으로 중단한다.

---

## 8. 사람 승인·반려와 PR 상태

사람 승인과 반려의 의미는 다음과 같이 구분한다.

- **승인:** PR이 `main`에 머지되어 `MERGED` 상태가 됨
- **반려:** PR을 머지하지 않고 닫아 `CLOSED` 상태가 됨

PR을 `CLOSED`로 만드는 것과 Issue를 `CLOSED`로 만드는 것은 별개다.
작업 자체를 폐기하려면 사람이 Issue 폐기를 명시적으로 결정해야 한다.

PR 진입 전 로컬 `npm run verify` PASS, Issue 종료 조건 전체 충족, 완료
코멘트 작성이 필요하며, PR과 CI의 구체적 진입·복귀 절차는
`docs/harness/03-loop.md`를 따른다.

## 9. 현재 공백과 미결정 사항

| 영역 | 상태 | 현재 값 |
|---|---|---|
| GitHub Issue 인덱스 | 미정(추후 생성) | 현재 0개 |
| 검증 규칙 | 초안 | `docs/harness/02-verification.md` |
| 검증 스크립트 | 참고·실행 수단 | 규칙의 원본은 `02-verification.md`이며, 개별 스크립트가 원본이 아님 |
| 구현·검증 루프 | 초안 | `docs/harness/03-loop.md` |
| 통합 운영 런북 | 미정(추후 생성) | 별도 원본 없음 |
| 배포·롤백 절차 | 미정(추후 생성) | 별도 원본 없음 |
| 백업·복구 절차 | 미정(추후 생성) | 실행 가능한 통합 원본 없음 |
| 장애 대응·모니터링 | 미정(추후 생성) | 별도 원본 없음 |
| 담당자·기한 | 미정(추후 생성) | 없음 |

빈칸이나 추정으로 공백을 채우지 않는다. 새 규칙이나 담당·기한은 해당
원본과 GitHub Issue가 생성된 뒤 등록한다.
