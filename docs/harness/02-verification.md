# Inventory Harness 검증 정책

> 이 문서는 현재 하네스의 검증 대상, 실행 방법, 결과 판정과 증거 형식을

> 기술 구조와 불변식은 [`../06-architecture.md`](../06-architecture.md),
> 원본 간 관계와 보호 정책은 [`01-SSOT.md`](./01-SSOT.md)를 따른다.

- **적용 기준:** `feature/add-harness-verification` 브랜치

- **기한:** 없음

## 1. 목적과 적용 범위

이 문서는 다음을 현재 하네스의 검증 범위로 정의한다.

- 요구사항과 아키텍처의 기준을 실행 가능한 검사 및 수동 절차에 연결한다.
- 정적 검사, 구조 검사, 도메인 테스트, 데이터 준비, 빌드, CI와 수동 QA를
  서로 다른 검증 계층으로 구분한다.
- 검증 결과를 재현 가능한 증거로 남기고, 실패·미검증·충돌을 구분한다.
- 구현을 변경한 뒤 검증하고 결과를 기록하는 최소 루프를 정한다.

이 문서는 `docs/01-requirements.md`의 업무 규칙이나
`docs/06-architecture.md`의 설계를 대신하지 않는다. 두 문서의 규칙을
검증하는 방법만 다룬다. `docs/07-plan.md`와 `docs/HANDOVER.md`는 아래에서
명시한 범위 안에서 참고 자료와 과거 증거로 사용하며, 그 내용 전체를
새로운 요구사항이나 검증 규칙으로 자동 승격하지 않는다.

`01-SSOT.md`의 5절(검증 규칙)과 6절(구현·검증 루프)은 이 문서 작성 전에는
미정이었다. 사용자의 요청에 따라 이제 이 문서를 해당 두 영역의 검증
원본으로 등록했다. 다만 문서 자체의 상태는 여전히 **초안**이며, 담당자·기한과
관련 Issue는 확정하지 않는다. 도메인·아키텍처 원본의 내용을 이 문서가
대체하지 않는다.

## 2. 권위와 증거의 구분

| 종류 | 문서·파일 | 이 문서에서의 역할 |
|---|---|---|
| 업무 원본 | `docs/01-requirements.md` | 도메인 의미, 범위, Definition of Done의 기준 |
| 아키텍처 원본 | `docs/06-architecture.md` | 구조, 데이터 흐름, 재고 불변식과 구현 제약의 기준 |
| 검증 정책 초안 | `docs/harness/02-verification.md` | 이 범위의 실행 순서, 상태, 증거, 실패 처리 |
| SSOT 거버넌스 | `docs/harness/01-SSOT.md` | 원본 우선순위, 승인, 충돌, 비밀 보호 기준 |
| 기존 계획 참고 | `docs/07-plan.md` | 마일스톤별 검증 절차와 QA 항목의 목록 |
| 현재 상태 참고 | `docs/HANDOVER.md` | 구현 현황과 과거 실행 결과 |
| 실행 증거 | `tests/`, `scripts/`, CI 실행 결과 | 실제 검사 코드와 특정 실행의 결과 |

원본 간 내용이 다르면 AI가 임의로 해소하지 않는다. 충돌한 원본과 영향
범위를 기록하고 **`NEEDS_HUMAN`**으로 표시한다. 문서에 적힌 과거 통과
기록이나 기대 결과만으로 새 실행을 `PASS`로 판정하지 않는다.

## 3. 결과 상태와 완료 판정

검증 항목은 다음 상태 중 하나로 기록한다.

| 상태 | 의미 |
|---|---|
| `PASS` | 지정된 명령 또는 절차를 실제 실행했고 기대 조건을 충족함 |
| `FAIL` | 실행했으나 기대 조건을 충족하지 못함 |
| `NOT_RUN` | 실행하지 않음. 문서나 추정만으로 통과시키지 않음 |
| `BLOCKED` | 구현·환경·권한 등으로 실행할 수 없음 |
| `NEEDS_HUMAN` | 원본 충돌, 예외 승인, 소유자·범위 판단이 사람에게 남음 |
| `HISTORICAL` | 과거 기록에만 근거하며 현재 기준으로 재실행하지 않음 |

자동 검증 게이트는 해당 게이트가 `PASS`여야 통과한다. 수동 검증은 실제
절차와 증거가 있는 경우에만 `PASS`이며, 자동 불변식을 수동 관찰만으로
대체할 수 없다. 한 항목의 완료 여부가 요구사항의 여러 조건에 걸쳐 있으면
각 조건을 따로 기록하고, 전체 완료를 추정하지 않는다.

## 5. 자동 검증 게이트

이 브랜치의 표준 실행 명령은 다음과 같다.

```bash
npm run verify
```

`verify`는 다음 순서로 실행된다.

```text
npm run verify:prepare
npm run typecheck
npm run lint
npm run architecture:check
npm run test
npm run build
```

앞 단계가 실패하면 뒤 단계는 실행하지 않고 실패한 명령과 결과를 기록한다.

### 5.1 준비 — `verify:prepare`

`scripts/reset-db.ts`가 `DATABASE_URL`이 가리키는 **폐기 가능한 SQLite
파일**과 SQLite sidecar 파일을 초기화한 뒤 `npm run db:ensure`로 마이그레이션과
시드를 준비한다. 다음을 지킨다.

- `DATABASE_URL`이 `file:` 형식인지 확인한다.
- 공유·운영·원격 데이터베이스에는 실행하지 않는다.
- 로컬 `prisma/dev.db`는 검증 후에도 커밋하지 않는다.
- 데이터 초기화가 필요한 별도 작업은 이 명령의 범위를 벗어난다.

초기화는 파괴적 작업이므로 대상이 불명확하면 실행을 중단하고 사람에게
확인한다. CI는 작업마다 격리된 SQLite 파일을 사용한다.

### 5.2 타입·린트

- `npm run typecheck`: `tsc --noEmit`이 오류 없이 종료되어야 한다.
- `npm run lint`: ESLint가 오류 없이 종료되어야 한다.

생성 파일이나 경고의 의미를 추정해 오류를 숨기지 않는다.

### 5.3 아키텍처 경계

`npm run architecture:check`는 TypeScript AST를 검사해
`lot.update`·`lot.upsert`·`lot.create` 및 `movement.update`·`movement.upsert`·
`movement.create`가 `src/lib/stock.ts` 밖에서 직접 호출되는지 확인한다.
재고 수량을 바꾸는 경로는 `applyMovement()` 하나여야 한다. 이 검사는
도메인 동작 전체를 증명하는 것이 아니라 직접 변경 경계를 검사한다.

### 5.4 테스트

`npm run test`는 Vitest로 `tests/**/*.test.ts`를 실행한다. 현재 테스트는
`prisma/dev.db`를 공유하므로 `vitest.config.ts`의
`fileParallelism: false` 설정을 유지하고, 테스트는 자신이 만든 데이터만
정리한다. 테스트가 통과해도 테스트에 포함되지 않은 화면·요구사항까지
통과했다고 판정하지 않는다.

### 5.5 빌드

`npm run build`는 Prisma Client 생성과 Next 빌드를 수행한다. 빌드 성공은
배포 승인이나 기능의 업무 완료를 의미하지 않는다.

> 참고: 이 문서가 기준으로 삼는 `feature/add-harness-ssot-policies` 계열
> 브랜치에는 위 통합 명령이 있다. `main`의 이전 기준 커밋에는
> `typecheck`, `architecture:check`, `verify:prepare`, `verify`가 없을 수
> 있으므로, 다른 브랜치에서 실행할 때는 먼저 `package.json`과 파일 존재를
> 확인한다. 없는 명령을 있는 것으로 기록하지 않는다.

## 6. CI 검증

`.github/workflows/verify.yml`은 다음 조건에서 `npm run verify`를 실행한다.

- `main`으로의 push
- `main`을 대상으로 하는 pull request
- `ubuntu-latest`, Node.js 20
- `npm ci`로 lockfile에 따른 의존성 설치
- 작업 전용 SQLite `DATABASE_URL`
- 작업 전용 세션 테스트 설정
- `contents: read` 권한

CI 성공은 특정 커밋과 특정 실행 환경에 대한 증거다. workflow 파일 자체가
도메인 규칙을 새로 만들지는 않는다. 로컬의 `npm install`과 CI의 `npm ci`는
각각 개발 설치와 lockfile 재현 설치라는 다른 목적을 가진다.

현재 이 문서가 작성된 브랜치와 `main`의 파일 구성이 다를 수 있으므로,
CI 결과에는 브랜치와 커밋 SHA를 함께 기록한다.

## 7. 수동 검증 경계와 현재 상태

수동 검증 목록은 `docs/07-plan.md` §2와 요구사항의 완료 기준을 참조한다.
목록에 있다고 해서 실행 완료를 뜻하지 않는다.

- S10: 검색과 가용 재고의 거점별 분해

### 7.2 과거 증거와 미검증

`docs/HANDOVER.md`에는 다음 과거 실행 결과가 기록되어 있다. 현재 커밋에서
재실행한 결과가 아니므로 `HISTORICAL`로만 취급한다.

- 자동 테스트 19개 통과와 빌드 성공
- 입고 → 출고 → 발송 → 도착 확인 → 일일 반영의 브라우저 확인
- 성수 팝업 누적 반출 160개, 잔여 42개, 시식 5개, 판매 113개 확인
- 팝업 정산 확정과 되돌리기 확인
- 관련 화면 캡처가 `docs/screenshots/`에 있다는 기록

같은 문서에는 `/expiry`, `/history`, `/settings`가 404이고 M7이 미구현이며,
한글 IME·긴 상품명·동시 출고 등 QA가 미검증이라고 적혀 있다. 이 항목은
현재도 `NOT_RUN` 또는 `BLOCKED`로 기록하고 실제 재검증 전에는 완료로
표시하지 않는다.

수동 검증이 자동 불변식과 다른 결과를 보이면 어느 한쪽을 임의로 우선하지
않고 원인과 영향 범위를 기록한 뒤 `NEEDS_HUMAN`으로 올린다.

## 8. 증거 기록 형식

각 실행 또는 수동 검증 기록에는 가능한 범위에서 다음을 포함한다.

| 필드 | 기록 내용 |
|---|---|
| 검증 ID | V-01 등 레지스트리 ID 또는 시나리오 ID |
| 기준 | 요구사항·아키텍처의 경로와 절 |
| 대상 | 명령, 파일, 화면 또는 시나리오 |
| 기준 코드 | 브랜치와 commit SHA |
| 환경 | OS, Node, 의존성 설치 방식, DB 종류 |
| 실행 시각 | 실제 실행 시각 |
| 기대 결과 | 원본에 근거한 판정 조건 |
| 실제 결과 | 출력 요약, 테스트 수, 관찰 내용 |
| 상태 | `PASS`/`FAIL`/`NOT_RUN` 등 §3 값 |
| 증거 링크 | CI 실행, 로그, PR, 이슈, 캡처 경로 |
| 담당·Issue | 확인된 경우에만 기록 |

로그·스크린샷·Issue·PR에는 토큰, 비밀번호, 세션 시크릿, 개인정보를 넣지
않는다. 데모 계정의 비밀번호나 CI 설정값도 증거에 복사하지 않고, 필요한
경우 테스트용 값의 존재만 기록한다.

## 9. 실패 처리와 재실행

1. 자동 게이트는 첫 실패 지점에서 멈춘다.
2. 실패한 명령, 커밋, 환경, 오류 요약과 상태를 기록한다.
3. 원인을 구현·테스트·아키텍처 위반·환경/의존성·DB 준비·문서 충돌 중
   가능한 범주로 분류한다.
4. 요구사항이나 아키텍처를 검증에 맞추어 조용히 약화하지 않는다.
5. 수정 후에는 폐기 가능한 DB를 다시 준비하고 표준 순서부터 재실행한다.
6. 이전 `FAIL`과 이후 `PASS`를 모두 관련 Issue/PR 증거에 남긴다.
7. 원본 충돌, 예외 승인, 담당자·Issue 부재에 따른 정책 결정은
   `NEEDS_HUMAN`으로 중단한다.

환경 문제로 실행하지 못한 것을 `FAIL`로 단정하지 않으며, 반대로 실행하지
않은 것을 환경이 정상일 것이라고 추정해 `PASS`로 만들지 않는다. 수동
검증 실패는 영향을 받은 시나리오를 명시하고, 전체 완료를 막는지 여부가
원본에 없으면 그 범위를 사람에게 확인한다.

## 10. 구현·검증 루프

1. 작업의 관련 GitHub Issue를 확인한다. Issue가 없으면 없음을 기록하고
   임의로 만들지 않는다.
2. 변경 대상이 업무 규칙인지, 아키텍처인지, 개별 구현인지 분류한다.
3. `01-requirements.md` 또는 `06-architecture.md`의 관련 절을 연결하고,
   원본과 충돌하면 `NEEDS_HUMAN`에서 멈춘다.
4. 승인된 범위만 구현한다.
5. 변경 유형에 맞는 검증을 실행한다. 가능하면 전체 게이트인
   `npm run verify`를 사용하고, 수동 검증은 시나리오 ID로 기록한다.
6. §8 형식으로 결과와 증거를 기록한다.
7. 실패하면 §9에 따라 원인을 수정·보고하고, 원본 내용을 임의로 바꾸지
   않는다.
8. 통과 결과도 기준 커밋과 실행 환경을 남긴 뒤 Issue/PR과 연결한다.
9. 요구사항·아키텍처·SSOT 자체를 바꿔야 할 때는 해당 원본 변경 승인과
   관련 Issue를 별도로 확보한다.

이 루프는 현재 문서 범위의 초안이다. 배포, 롤백, 백업·복구, 장애 대응,
모니터링의 운영 절차를 정의하지 않으며, 그 영역의 담당자·기한도
확정하지 않는다.

## 11. 커버리지와 미결정 사항

| 영역 | 현재 연결된 검증 | 현재 공백 |
|---|---|---|
| 재고 원장·Lot 불변식 | `stock-invariant.test.ts`, 아키텍처 원본 | 현재 실행 증거는 실행별로 별도 기록 필요 |
| FEFO·LEFO | `fefo.test.ts` | 화면 전체 흐름은 수동 확인 필요 |
| 팝업 누적 정산 | `popup-settle.test.ts`, 브라우저 과거 기록 | 현재 기준 재실행 여부 |
| 시드·홈 대표 로트 | `verify-m1.ts`, `verify-headline.ts` | npm/CI 게이트 연결 여부와 실행 기록 |
| 화면·접근성·반응형 | `07-plan.md` 목록, 브라우저 절차 | IME·긴 이름·터치·동시성 등 미검증 |
| M7 기능 | 요구사항과 QA 목록 | `/expiry`, `/history`, `/settings`, 조정·폐기 미구현 기록 |

다음 사항은 현재 문서에서 미정으로 남긴다.

- 검증 규칙의 최종 담당자, 기한, 관련 GitHub Issue
- `verify-m1.ts`와 `verify-headline.ts`를 공식 자동 게이트로 연결할지 여부
- 브라우저 자동화 도구와 접근성 판정의 표준
- 배포·롤백·백업·복구·장애 대응 검증의 별도 원본

위 사항을 정할 때는 근거와 영향 범위를 함께 기록하고, 원본 간 충돌이
있으면 `NEEDS_HUMAN` 절차를 따른다.

## 12. 변경 관리

- 도메인 검증 기준을 바꾸려면 `docs/01-requirements.md`의 관련 절과
  Issue를 먼저 확인한다.
- 구조·불변식 검증 기준을 바꾸려면 `docs/06-architecture.md`의 관련 절과
  Issue를 먼저 확인한다.
- 실행 순서, 상태, 증거 형식을 바꾸려면 이 문서의 변경 이유와 영향을
  기록한다.
- 원본 레지스트리와 SSOT 우선순위를 바꾸려면 `01-SSOT.md`를 별도 승인
  범위에서 갱신한다.
- 테스트·스크립트·CI의 현재 상태를 문서에 반영할 때는 실제 파일과 실행
  결과를 확인한다.
- 새 규칙이나 예외를 근거 없이 추가하지 않고, 사람이 승인하지 않은
  파괴적 작업·원격 변경·커밋·푸시는 수행하지 않는다.
